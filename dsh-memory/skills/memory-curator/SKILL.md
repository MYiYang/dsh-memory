# 记忆维护（memory-curator）

记忆系统的价值 = 准确率 × 可召回率。**错误记忆比没有记忆更贵**：它会被当成事实反复使用。

## 1. 什么值得存（fact 的四条判据）

存，当且仅当满足其中两条以上：

1. **跨会话仍然成立**（偏好、约定、架构决策、环境事实、外部系统地址）。
2. **重述成本高**（一段排查结论、一个踩坑原因、一个业务规则）。
3. **说错了会出事**（「不要动鉴权模块」「生产库只读」）。
4. **用户明确要求记住**（「以后都这样」）。

不存：一次性任务细节、临时路径、模型的中间推理、大段工具输出、能从仓库/文档随时读到的内容。

判断句：**「下个会话的新 Agent 需要知道这条吗？」** 如果不会，就别存。

## 2. 三种记忆用对类型

| kind | 用途 | 例子 |
| --- | --- | --- |
| `fact` | 稳定的结论、偏好、约束 | 「用户要求回答用简体中文，代码注释用英文」 |
| `episode` | 一次完整交互的过程记录（自动捕获） | 「用户问 dsh 加记忆，最终定了原生插件方案」 |
| `note` | 待验证的观察、半成品结论 | 「疑似 CI 不跑测试，待确认」 |

`fact` 要写成**主谓明确、可执行**的句子，不要写「讨论过 X」；`note` 要带「待确认」标记，确认后升级为 `fact` 或删除。

## 3. 冲突处理（最重要的一节）

新旧事实冲突时，不要简单追加：

1. 先 `memory_search` 找到旧条目（同主题多条会一起召回）。
2. 判三种关系：
   - **替代**：新结论否定旧结论 → 删旧的，存新的（并存会随机命中错误答案）。
   - **细化**：新结论是旧结论的子情况 → 合并成一条更精确的 fact。
   - **并存**：两者在不同条件下都成立 → 都保留，并在文本里写清适用条件（「Windows 下用 pwsh」「Linux 下用 bash」）。
3. 改完做一次 `memory_search` 自检：只应该召回新版本。

## 4. 定期体检（每周或记忆 > 200 条时）

- `memory_stats`：看 facts/episodes 比例与库大小；episodes 过多说明只进不出。
- `memory_list` 抽样最近 20 条：有没有重复、过期、无主语的句子。
- 清理三类垃圾：一次性任务 episode（>30 天且从未被召回）、过期路径/地址、被新事实替代的旧条目。
- 保留策略建议：`fact` 永久（除非被替代），`episode` 90 天后按 `use_count` 淘汰，`note` 30 天未升级就删。

## 5. 召回不好用的排查顺序

1. **完全没召回** → 查查询词：2 字中文词命中不了 trigram 索引，会回退 LIKE；纯符号/数字查询基本无解，改用自然语言描述。
2. **召回无关内容** → 降 `maxItems`（默认 6→4）、升 `minScore`（0.2→0.35）、把模糊内容标成 `note`。
3. **旧结论压过新结论** → 说明没做冲突清理，回到第 3 节。
4. **上下文被记忆挤爆** → 降 `maxChars`（1400→800）；记忆应该「少而准」，不是「多而全」。
5. **跨项目串味** → 检查条目 scope：项目内的结论用 `scope: project`，只有真正通用的偏好才用 `global`。

## 6. 写入前的三秒自检

- 这句话脱离上下文还成立吗？
- 三个月后它还成立吗？
- 它和已有记忆冲突吗（先搜一遍）？
- 换一个人/Agent 读，会不会误解？

四个问题都过，再 `memory_save`。
