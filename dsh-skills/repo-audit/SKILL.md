# 开源仓库审计（repo-audit）

目标不是「读完代码」，而是**在有限时间内产出可复核、可决策的结论**：它是什么 / 怎么跑 / 设计强在哪 / 坑在哪 / 值不值得用。

## 0. 先定边界（5 分钟）

1. 确认**默认分支**（`git ls-remote --symref <url> HEAD`）。默认分支经常不是 `main`，而且 `main` 可能是被遗弃的旧产品线——先对比两者文件数，再决定审计哪条。
2. 记录时间点：commit sha、日期、star/fork/open issues 数（结论里必须带基线）。
3. 判断规模：`git ls-files | wc -l`、按顶层目录统计文件数/行数。**>50k 行就必须并行**，不要串行读。

## 1. 建本地快照（网络受限时的关键一步）

如果 shell 直连 GitHub 失败（DNS 被拦、TLS 失败），不要放弃整仓审计：

- 用 GitHub API 拿完整文件树：`GET /repos/{o}/{r}/git/trees/{sha}?recursive=1`（`truncated=false` 才算完整）。
- 内容用 jsDelivr CDN 逐文件拉：`https://cdn.jsdelivr.net/gh/{o}/{r}@{ref}/{path}`（`@ref` 可带斜杠分支名）。
- 跳过大二进制（png/jpg/mp4/zip），其余全拉，落在 `repo/`；记录 `skipped` 与 `failures` 清单。
- 拉完校验：文件数 = 树里 blob 数 − skipped，且抽查 3 个文件首行。

## 2. 四路并行（把上下文当预算）

每个子代理一个不重叠的写入范围（`notes/A.md`…），任务书必须包含「必须覆盖的问题清单 + 证据格式（文件:行号）+ 输出字数上限」。推荐切法：

| 路线 | 范围 | 必答 |
| --- | --- | --- |
| A 核心 | 领域逻辑/算法/存储 | 数据模型、写路径、读路径、降级矩阵、性能隐患 |
| B 服务端 | HTTP/鉴权/配置/可观测 | 端点全景、鉴权层次、危险默认、错误码一致性 |
| C 前端/旁路 | UI、知识库、SDK | 技术栈、前后端契约、密钥处理、完成度 |
| D 部署/生态 | deploy、插件、CI、CHANGELOG | 部署矩阵、接入矩阵、CI 实际检查项、版本口径 |

同时自己读：根 README/INSTALL/CHANGELOG/ROADMAP + metadata（release/tag/commit/issue/PR），负责最终判断。

## 3. 必查的「硬证据」（比读代码更快暴露问题）

- **测试**：`git ls-files | grep -Ei '(\.(test|spec)\.|__tests__)'`。数量为 0 而 README 宣称有测试 → 直接记「文档-代码不一致」。
- **CI**：`cat .github/workflows/*.yml`，看触发分支是否等于默认分支、是否跑 lint/typecheck/test。这两条经常同时翻车。
- **默认安全**：`grep -rn "0.0.0.0\|API_KEY\|requireAuth\|fail-open"` → 是否「非回环 + 空密钥只 warn 不拒绝」。
- **隔离**：搜 `tenant|isolation|user_id|team_id`，看检索路径是否真的带过滤，而不是只写在类型里。
- **文档漂移**：把 README 引用的路径全部 `test -e` 一遍；版本号在 package.json / CHANGELOG / ROADMAP / 镜像 tag 四处对比。
- **重复与死代码**：同一算法（如 RRF）出现 N 份、自称「消除重复」的工具函数无人 import → 维护债信号。

## 4. 出报告的结构（照这个写，决策者能直接读）

1. 一页速览：是什么 + 一句话判断 + 分维度评分表（每格带证据）。
2. 定位与生态位：解决什么问题、和 RAG/竞品的差别。
3. 仓库地图与规模表。
4. 架构与数据流（写入/读取两条时序）。
5. 核心机制拆解（含降级矩阵表）。
6. 工程质量（测试/CI/巨型文件/重复实现/版本漂移）。
7. 安全与隐私分级表（级别｜问题｜位置｜影响｜建议）。
8. 社区健康度。
9. 采用建议（适合谁/不适合谁/最小加固清单/可借鉴设计）。
10. 局限与待确认项 + 附录（关键文件索引、复核命令）。

## 5. 纪律

- 每条结论都要能落到 `path:line`；落不到就降级为「推测」并标注。
- 不运行被审计项目的代码（除非用户要求），性能/Benchmark 一律标「未验证」。
- 区分「代码缺陷」和「部署默认值缺陷」——后者往往更致命（默认裸奔 > 逻辑漏洞）。
- 结论要给**行动**：最小加固清单、适配改造点、或明确的「暂时别用，因为 X」。
